Свака ставка одговара једном реду табеле из одељка 3.1 документације.

## Захтев 1 - База, шеме, демо подаци
`db/01_baza_i_seme.sql`, `db/04_demo_podaci.sql` · тестови `T01`, верификација V1-V7 у самој скрипти

База `[BugTracker]` са колацијом `Serbian_Cyrillic_100_CI_AS` (`CI` = не
разликује велика и мала слова, `AS` = разликује акценте). Скрипта прво провери
да ли колација уопште постоји на инстанци и прекида рад изузетком ако не постоји
- иначе би тихо настала база у којој се ћирилица погрешно сортира.

Четири шеме: `impl` (приватна имплементација АТП-а), `spec` (јавна
спецификација), `api_dev` и `api_qa`. Све у власништву `dbo`, што је услов за
*ownership chaining* - механизам захваљујући коме апликација чита податке из
`impl` табела иако над њима нема ниједну дозволу.

Демо подаци су дословно из табела 1-3 документације. Због `SET IDENTITY_INSERT`
идентификатори су тачно 1,2,3 / 1..4 / 1,2 као у документацији. Поред та два
коментара додато је још пет, јер их аплиакција стварно ствара из форме, а без
њих екрани „Детаљи грешке“ и „Активност аутора“ немају шта да прикажу.

## Захтев 2 - Табеле, ограничења, каскада, тригер
`db/02_tabele.sql`, `db/03_impl_interno.sql` · тест `T02`

Три пословне и две техничке табеле, 27 именованих ограничења, четири индекса.

Структурна правила интегритета из табеле 6 решена су **декларативно**, једним
страним кључем по вези:

* `FK_Greska_Projekat ... ON DELETE NO ACTION` покрива два реда СПИ табеле
  одједном - Restrict при уносу грешке са непостојећим пројектом и Restrict при
  брисању пројекта који има грешке.
* `FK_Komentar_Greska ... ON DELETE CASCADE` реализује ред
  „ГРЕШКА / Delete → Cascade (КОМЕНТАР)“.

Асиметрија је намерна: коментар без грешке је бесмислен, а грешка је самостална
информација коју не смемо тихо изгубити.

Провера да XML садржи `<tekst>` није могла директно у `CHECK` - сервер то
изричито забрањује (`Msg 423`) и сам предлаже решење, па постоји функција-омотач
`impl.fnsImaTekst` коју `CHECK` позива.

Индекси (НЗ 8 тражи префикс `idx`) нису украс - сваки стоји иза неког екрана:
`idxGreskaProjekat` за листу грешака једног пројекта и за матрицу,
`idxGreskaStatus` (филтриран, само два статуса) за екран отворених грешака,
`idxKomentarGreska` за детаље грешке, `idxIstorijaGreska` за историју.

Тригер `trgAutoStatusResen` спроводи право пословно правило: када програмер у
форми попуни поље „решење“, апликација пошаље `<resenje>` у XML-у, а база сама
пребаци грешку у статус `Решена`. Корисник не мора посебно да мења статус.
Писан је **скуповно**, јер се тригер окида једном по наредби а не по реду.
Пошто SQL Server не дозвољава XML методе над `inserted`/`deleted`, редови се
прво препишу у табеларну променљиву.

## Захтев 3 - Процедуре, изузеци, `tblErrorLog`
`db/07_upravljanje_greskama.sql` · тест `T03`

Све процедуре су `WITH ENCRYPTION` (`OBJECT_DEFINITION` враћа `NULL`) и иду по
истом костуру: `SET NOCOUNT ON; SET XACT_ABORT ON;` → `TRY` са валидацијама које
бацају изузетке 50010-50060 са порукама **дословно преписаним из табела СПИ и
ВПИ** → трансакција → `CATCH` који поништи трансакцију, упише грешку у
`impl.tblErrorLog` и врати оригиналну грешку са `THROW;`.

Логовање иде **после** `ROLLBACK`-а - иначе би и упис у дневник био поништен.

Иста правила проверавају и `CHECK` ограничења и процедуре: `CHECK` је последња
линија одбране и важи без обзира којим путем подаци стижу, али даје техничку
поруку на енглеском; процедура враћа пословну поруку коју апликација прикаже
кориснику.

`upr_DodajKomentar` прима **поља форме**, не XML - база сама склапа документ
преко `FOR XML PATH`. Тако је `<tekst>` гарантовано присутан, а знакови су
исправно екраписани. Необавезни делови (`<prioritet>`, `<okruzenje>`, `<oznake>`)
се једноставно не појаве ако корисник није попунио та поља.

## Захтев 4 - Погледи и `api_` слој
`db/08_pregledi.sql` · тест `T04`

`spec.vw_GRESKA` (са називом пројекта, како захтев тражи), `spec.vw_KOMENTAR`
(XML распакован у колоне) и `spec.vw_OTVORENE_GRESKE` (гради се **над**
`vw_GRESKA`, да спајање постоји само на једном месту).

`api_dev` и `api_qa` садрже танке омотаче без иједне пословне провере, по
конвенцији НЗ 8: PascalCase процедуре, UPPER_CASE погледи, camelCase параметри.
Обе шеме имају и синоним `DOZVOLJENI_STATUSI` - трећу кутију из дијаграма
архитектуре - из ког апликација пуни падајућу листу статуса.

Слој `api_` намерно **није** шифрован: `spec` је имплементација коју кријемо,
`api_` је уговор који програмер треба да прочита.

Разлика двеју API шема је конкретна, а не формална: `api_dev.KOMENTARI` има
колону `SirovXML` (програмеру треба при дијагностици), `api_qa.KOMENTARI` је
нема; `api_qa` уместо тога има `SAZETAK_PROJEKATA` и `PREGLED_PROJEKATA`, а
нема ниједну процедуру која мења податке.

## Захтев 5 - Улоге и изолација
`db/14_dozvole.sql` · тестови `T05_izolacija_DEV`, `T05_izolacija_QA`

`GRANT SELECT, EXECUTE, VIEW DEFINITION ON SCHEMA::api_dev TO DataProviderDEV`
и исто за QA над `api_qa`. Обема је изричито `DENY`-овано све над `impl`, `spec`
и над туђом API шемом. Логини имају само `CONNECT`.

Изолација је проверена **стварним повезивањем као апликација**, не као `sa`:

| Покушај као `DataProviderDEV` | Исход |
|---|---|
| `SELECT api_dev.GRESKE` | дозвољено |
| `EXEC api_dev.PrijaviGresku` | дозвољено |
| `EXEC api_dev.MatricaGresaka` | дозвољено |
| `SELECT impl.tblGreska` | **одбијено** |
| `SELECT spec.vw_GRESKA` | **одбијено** |
| `EXEC spec.upr_PromeniStatus` | **одбијено** |
| `SELECT api_qa.GRESKE` | **одбијено** |

Пре позива `sp_setapprole` одбијен је чак и приступ сопственој шеми - украдена
лозинка логина не вреди ништа. `USER_NAME()` се после активације мења из
`AppUserDEV` у `DataProviderDEV`: апликациона улога **замењује** идентитет.

Иста табела, два исхода - кроз поглед пролази, директно не. То је *ownership
chaining*: пошто су све шеме у власништву `dbo`, при пролазу кроз поглед провера
дозвола над `impl` се уопште не извршава.

## Захтеви 6 и 7 - Full-Text претрага
`db/05_fulltext.sql`, `db/10_pretraga.sql` · тестови `T06`, `T07`

Каталог `ftBugTracker` и три индекса: `tblGreska(Poruka)`, `tblProjekat(Opis)` и
`tblKomentar(SadrzajXML)`, сви са `KEY INDEX` = примарни кључ,
`CHANGE_TRACKING = AUTO` и **`LANGUAGE 3098` (Serbian Cyrillic)**.

Избор језика није формалност: word breaker сече текст на речи, а stemmer налази
облике исте речи. Са подразумеваним енглеским (1033) ћирилица би се секла само
по размацима. Инстанца стварно има српски ћирилички word breaker - провера у
тесту `T06`, преко речника индекса `sys.dm_fts_index_keywords`.

Попуњавање индекса је асинхроно, па скрипта чека `PopulateStatus = 0`.

Апликације нуде **два режима претраге**, што и јесте практична разлика између
два предиката:

| | режим `C` - напредна (`CONTAINS`) | режим `F` - слободна (`FREETEXT`) |
|---|---|---|
| Тражи | тачно задате речи | смисао, са облицима речи |
| `AND`, `OR`, `AND NOT`, `NEAR` | подржано | не подржава |
| Џокер `реч*` | подржано (у наводницима) | не подржава |
| Вишечлани низ без оператора | **синтаксна грешка** `Msg 7630` | ради |
| Кориснику | напредни филтери | обично поље „претражи“ |

Демонстрација на истим подацима (тест `T07`): за једну тачну реч оба режима дају
исто; за низ `корисник лозинка пријава` `CONTAINS` пуца, а `FREETEXT` враћа
грешку 1. Рангирање је показано преко `CONTAINSTABLE`/`FREETEXTTABLE`, које уз
`[KEY]` враћају и `[RANK]` (0-1000) - за тај упит `FREETEXTTABLE` даје грешци 1
ранг 216, осталима 0.

У `spec` постоје **две одвојене функције** уместо једне са параметром режима.
Прва верзија је покушала једну inline функцију са два `UNION ALL` гранa и
условима `WHERE @rezim = 'C'`/`'F'` - не ради, јер се `WHERE` примењује после
извора редова, па се `CONTAINSTABLE` изврши и над freetext упитом и пукне.
Inline функција нема `IF`/`ELSE`, па гранање мора у процедуру
`spec.upr_PretraziGreske`.

## Захтев 8 - CLR агрегатна функција
`clr/BugTrackerCLR/SpojPoruke.cs`, `db/06_clr_uda.sql` · тест `T08`

Агрегат `SpojPoruke` спаја поруке грешака у један стринг. Стоји иза QA екрана
„Сажетак по пројекту“, преко `spec.vw_SAZETAK_PROJEKATA` →
`api_qa.SAZETAK_PROJEKATA`.

Имплементиране су све четири методе животног циклуса и интерфејс
`IBinarySerialize`:

| Метода | Када | Шта ради |
|---|---|---|
| `Init()` | једном по групи | празан `StringBuilder` |
| `Accumulate()` | једном по реду | прескаче `NULL` и празне низове, иначе дописује |
| `Merge()` | при паралелном извршавању | спаја делимична стања |
| `Terminate()` | једном по групи | враћа стринг, или `NULL` за празну групу |
| `Write` / `Read` | (де)серијализација стања | исти редослед: `bool`, па `string` |

`Format.UserDefined` је обавезан јер стање садржи `StringBuilder` променљиве
дужине, и управо он **захтева** `IBinarySerialize`. `MaxByteSize = -1` смео се
навести само уз тај формат.

**Изградња на macOS-у:** SQLCLR извршава искључиво .NET Framework склопове, а
Framework на macOS-у не постоји. Решава га NuGet пакет
`Microsoft.NETFramework.ReferenceAssemblies`, који доноси референтне склопове.

**`clr strict security`:** од 2017 сви CLR склопови се третирају као `UNSAFE`, па
непотписан склоп пуца (`Msg 10343`). Уместо гашења заштите употребљена је
`sp_add_trusted_assembly` - база памти **SHA2_512 хеш** склопа и верује баш њему.
Тест `T08` показује да је заштита остала укључена (`value_in_use = 1`), а склоп
ипак учитан. Ако се склоп промени, промени се и хеш и поверење пада.

## Захтев 9 - FLWOR XQuery
`db/11_izvestaji_xml.sql` · тест `T09`

`spec.fns_AktivnostAutoraXml()` враћа извештај о активности аутора као XML - то
је QA ставка „Извези извештај“, коју апликација сними као `.xml` фајл.
`spec.fnt_AktivnostAutora()` је исти извештај распакован у редове помоћу
`.nodes()`, за приказ у менију.

XQuery ради унутар једног документа, а коментари су у седам засебних XML
вредности, па их прво `FOR XML PATH('kom'), ROOT('komentari'), TYPE` спаја у
један.

**SQL Server подржава XQuery 1.0, који нема клаузулу `group by`** - она је тек у
верзији 3.0. Груписање се зато ради обрасцем `distinct-values()` за кључеве +
угнежђени `for` за чланове групе. `count()` се користи у `order by`, у `where`
(тест `T09` показује варијанту само са ауторима који имају два и више коментара)
и у самом резултату као атрибут.

Друга специфичност: сервер статички проверава кардиналност, па изрази у
`order by` и `string()` морају бити гарантовано једночлани - пишу се као
`(израз)[1]`. Без тога `Msg 2389: requires a singleton`.

## Захтев 10 - Axis specifiers
`db/03_impl_interno.sql`, `db/11_izvestaji_xml.sql` · тест `T10`

Осе нису показане засебним примерима - уграђене су у објекте које апликација
свакодневно зове:

| Оса | Где живи | Чему служи |
|---|---|---|
| `child::` | `impl.vwKomentarDetalji` | чита `<tekst>` и `<prioritet>` као **директну децу** `<kom>`, да нас случајно угнежђен елемент дубље не превари |
| `descendant-or-self::` | `impl.vwKomentarDetalji`, `spec.fnt_OznakeGreske` | налази `<os>`, `<pregledac>` и `<oznaka>` на **било којој дубини**, да формат коментара може да се прошири без измене упита |
| `parent::` | `spec.fnt_OkruzenjaGreske`, `spec.fnt_GreskePoSistemu` | чвор идентификујемо по `<os>`, а треба нам и његов **брат** `<pregledac>`; пут до брата иде преко родитеља |

`parent::` ту није украс: SQL Server од обрнутих оса подржава **само** њу - нема
`ancestor::`, `ancestor-or-self::`, `following-sibling::` ни `preceding-sibling::`.
Подржано је шест оса: `child`, `descendant`, `descendant-or-self`, `parent`,
`attribute`, `self`.

Тест `T10` бројачки доказује да је `//oznaka` само пречица за
`/descendant-or-self::node()/child::oznaka` - оба израза дају исте вредности за
сваки коментар.

## Захтев 11 - `CONTAINS()` + `xml.nodes()`
`db/07_upravljanje_greskama.sql` · тест `T11`

`spec.upr_NadjiPoTerminu @termin` стоји иза ставке менија „Нађи по термину“ у
обе апликације. Комбинује два механизма:

| Механизам | Улога |
|---|---|
| `CONTAINS(k.SadrzajXML, @ftUpit)` | **груби филтер** - брзо, преко инвертованог индекса, сужава скуп редова |
| `CROSS APPLY k.SadrzajXML.nodes('/kom//*[not(*)]')` | **фини филтер** - сецка XML на чворове-листове и каже у ком елементу је погодак |

`local-name(.)` враћа име тог елемента. Путања `'/kom//*[not(*)]'` узима елементе
без елемената-деце (листове) на било којој дубини; прва верзија је користила
`/kom/*` и добијала слепљен текст пододељака.

Најбољи доказ да комбинација има смисла: термин `Android` **не постоји ни у
једном `<tekst>`** - налази се само у `<os>`. `CONTAINS` га нађе (индексира цео
XML садржај), а `nodes()` каже тачно у ком елементу.

## Захтев 12 - PIVOT матрица (оцена 10)
`db/07_upravljanje_greskama.sql` · тест `T12`

`spec.upr_MatricaGresaka @idProjekta = NULL` даје број грешака по пројекту у
колонама по озбиљности 1-5, плус збир. То је почетни QA извештај.

Употребљен је **статички** PIVOT јер је скуп озбиљности фиксиран ограничењем
`CK_Greska_Ozbiljnost`. Колоне су унапред познате: план се кешира, нема склапања
SQL-а у стрингу ни ризика од SQL injection-а. Динамички PIVOT био би потребан
само да вредности нису унапред познате.

Два детаља која се лако превиде:
* `PIVOT` имплицитно ради `GROUP BY` по **свим** колонама извора које нису ни
  агрегациона ни `FOR` колона. Зато извор вуче само пет колона - да смо додали и
  `DatumPrijave`, добили бисмо по један ред по датуму.
* `LEFT JOIN` је обавезан: кардиналност је `ПРОЈЕКАТ (0,M) ГРЕШКА`, па се пројекат
  без грешака мора појавити са нулама. За такав ред је `Ozbiljnost` `NULL`, не
  упада ни у једну колону, а `COUNT(NULL)` даје 0.

**Именовање:** захтев дословно тражи процедуру `upr_MatricaGresaka` у `api_qa`,
док НЗ 8 прописује PascalCase за процедуре у `api_*`. Документација је ту сама са
собом у сукобу, па постоје оба имена - `api_qa.upr_MatricaGresaka` и
`api_qa.MatricaGresaka` - оба само прослеђују позив у `spec`, без дупле логике.

## Захтев 13 - `OUTPUT` клаузула (оцена 10)
`db/07_upravljanje_greskama.sql`, `db/03_impl_interno.sql` · тест `T13`

`OUTPUT` даје приступ псеудо-табелама `inserted` и `deleted` - истим онима из
тригера - али **директно у DML наредби**:

```sql
UPDATE  impl.tblGreska
SET     StatusGr = @noviStatus
OUTPUT  deleted.Id, deleted.StatusGr, inserted.StatusGr
INTO    impl.tblHistorijaStatusa (IdGreske, StariStatus, NoviStatus)
WHERE   Id = @idGreske AND StatusGr <> @noviStatus;
```

Колоне `DatumPromene` и `Korisnik` се не наводе - попуњавају их `DEFAULT`
ограничења. Услов `StatusGr <> @noviStatus` спречава упис „промене“ из X у X.

**Зашто `OUTPUT`, а не тригер за архивирање:** тригер је одвојен објекат па онај
ко чита `UPDATE` не види да се архивира; овако је у истој наредби, у **истом DML
кораку**, што захтев изричито тражи.

Тригер `trgAutoStatusResen` такође мења статус, па је и његов `UPDATE` добио
`OUTPUT` - архива бележи и ручне и аутоматске промене, без рупа.

**Ограничења циљне табеле** доказана су уживо у тесту `T13`: привремено додато
`CHECK` ограничење изазива

> `The target table 'impl.tblHistorijaStatusa' of the OUTPUT INTO clause cannot
> have any enabled check constraints or any enabled rules.`

Циљна табела не сме имати укључене тригере, учествовати ни на једном крају
страног кључа, ни имати `CHECK`. Зато `tblHistorijaStatusa` нема страни кључ ка
`tblGreska` иако логички упућује на њу, а поглед `spec.vw_ISTORIJA_STATUSA` из
истог разлога користи `LEFT JOIN` - ред о обрисаној грешци сме да преживи.

*Име `tblHistorijaStatusa` није на српском („историја“), али је задржано зато
што га документација у захтеву 13 наводи дословно; имена која спецификација
прописује нису мењана.*

**Најважније за одбрану:** заглавље процедуре `spec.upr_PromeniStatus` се није
мењало када је додато архивирање, па се ни `api_dev.PromeniStatus` ни C#
апликација не мењају. Имплементација је добила нову функционалност, а уговор
према апликацији је остао исти - то је живи доказ да енкапсулација АТП-а ради.
